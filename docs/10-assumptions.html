10.2.1 How many observations are we actually working with?

Before running a formal test, check how large the analysis sample is. This is not the same as the number of rows in the file:

nrow(star)      # rows in the dataset
[1] 6325
nrow(aug)       # rows the model actually used
[1] 4756

Those two numbers differ, sometimes substantially. lmer() drops any case missing a value on the outcome or on any predictor, a behavior called listwise deletion, and it does so silently. Adding one predictor with a lot of missingness can shrink your analysis sample dramatically without any warning appearing.

This matters for more than the diagnostics below. If you compare two models fit on different subsamples, the comparison is not valid, which is why the N row in a results table is worth reading rather than skipping. It is also the reason to check missingness before modeling rather than after.

10.2.2 A formal test, with a caveat

# Shapiro-Wilk accepts between 3 and 5,000 observations, so sample if needed
if (nrow(aug) > 5000) {
  set.seed(664)
  shapiro.test(sample(aug$std_resid, 5000))
} else {
  shapiro.test(aug$std_resid)
}

    Shapiro-Wilk normality test

data:  aug$std_resid
W = 0.99119, p-value < 2.2e-16

Expect this to be significant, and do not make much of it. Shapiro-Wilk detects arbitrarily small departures from normality once the sample is reasonably large, and at these sample sizes it will reject for essentially any real dataset. The histogram and Q-Q plot carry the information here. What you are looking for is severe skew, heavy tails, or obvious multimodality, not a p-value.

It is also worth remembering what this assumption buys. Normality of residuals matters for small-sample inference. With samples this size, the central limit theorem does most of the work regardless.

A silent failure worth knowing about

Writing gktchid = names(cooks) looks reasonable and is wrong here, because cooks.distance() on an influence.ME object returns a matrix whose labels live in rownames(). names() on that matrix returns NULL.

The dangerous part is what happens next. tibble() drops NULL columns without complaint, so you get a one-column data frame and no error. Everything that uses only cooks_d keeps working, including the plot below. The failure surfaces later, at the first line that asks for gktchid, which may be several chunks away from the line that actually caused it.

When a variable goes missing without explanation, look upstream for the place it was created, not at the line that reported the error. Running str() on an unfamiliar object before you build a data frame from it costs a second and prevents this whole category of problem.

cutoff <- 4 / nrow(cook_df)

ggplot(cook_df, aes(x = seq_along(cooks_d), y = cooks_d)) +
  geom_point(alpha = 0.6, color = "#1a7a6e") +
  geom_hline(yintercept = cutoff, linetype = "dashed", color = "#b2182b") +
  labs(title = "Cook's Distance by Classroom",
       subtitle = paste0("Dashed line at 4/n = ", round(cutoff, 4)),
       x = "Classroom index", y = "Cook's distance") +
  theme_minimal()

When a case is flagged, look at it before doing anything. A classroom with an implausible value, a math score of 9999 or a class size of 200, is a data error and should be fixed or removed. A classroom that is simply unusual, small and high-achieving, is data. Deleting inconvenient observations because a statistic flagged them is not a diagnostic procedure, it is a way of guaranteeing the result you already wanted.

Do not pass cluster = star$gktchid here

The obvious thing to write is coef_test(m, vcov = "CR2", cluster = star$gktchid), and it fails with arguments must have same length.

The reason is the listwise deletion we looked at earlier in this chapter. star$gktchid has one entry per row of the dataset, while the model was fit on the smaller set of complete cases. The two vectors do not line up, and clubSandwich cannot tell which classroom each residual belongs to.

Omitting the argument is the reliable fix, because the fitted model already carries its grouping factor and knows which rows it used. If you do need to supply the cluster explicitly, take it from the model frame rather than the original data:

mf <- model.frame(m)
coef_test(m, vcov = "CR2", cluster = mf$gktchid)

This is a specific instance of a general habit worth forming. Once a model has been fit, prefer model.frame(), augment(), or the model object itself over the data frame you started with. Anything derived from the original data risks being the wrong length.

10.6 Writing it up

A sensitivity analysis paragraph belongs in nearly every quantitative paper, and it has a predictable shape. State which diagnostics you examined. Report what they showed, honestly, including the parts that looked imperfect. Describe the robustness checks you ran. Then state whether your substantive conclusion held.

The version that reads as defensive says the assumptions were met and moves on. The version that reads as competent concedes that residuals showed mild right skew and 14 classrooms exceeded the conventional Cook’s distance threshold, then reports that the class size estimate changed by less than a tenth of a point under cluster-robust standard errors and with those classrooms excluded. The second version is more honest and considerably more persuasive.

```{r}
grp_labels <- rownames(cooks)
if (is.null(grp_labels)) grp_labels <- names(cooks)
if (is.null(grp_labels)) grp_labels <- as.character(seq_len(length(cooks)))

cook_df <- tibble(
  gktchid = grp_labels,
  cooks_d = as.numeric(cooks)
)

cook_df |> arrange(desc(cooks_d)) |> head(10)
```

::: {.callout-warning}
## A silent failure worth knowing about

Writing `gktchid = names(cooks)` looks reasonable and is wrong here, because `cooks.distance()` on an `influence.ME` object returns a matrix whose labels live in `rownames()`. `names()` on that matrix returns `NULL`.

The dangerous part is what happens next. `tibble()` drops `NULL` columns without complaint, so you get a one-column data frame and no error. Everything that uses only `cooks_d` keeps working, including the plot below. The failure surfaces later, at the first line that asks for `gktchid`, which may be several chunks away from the line that actually caused it.

When a variable goes missing without explanation, look upstream for the place it was created, not at the line that reported the error. Running `str()` on an unfamiliar object before you build a data frame from it costs a second and prevents this whole category of problem.
:::

When a case is flagged, look at it before doing anything. A classroom with an implausible value, a math score of 9999 or a class size of 200, is a data error and should be fixed or removed. A classroom that is simply unusual, small and high-achieving, is data. Deleting inconvenient observations because a statistic flagged them is not a diagnostic procedure, it is a way of guaranteeing the result you already wanted.

## The part that settles it: robustness checks

Rather than arguing about whether assumptions hold, refit the model under different assumptions and compare.

```{r}
#| message: false

library(clubSandwich)

# Cluster-robust standard errors.
# clubSandwich reads the clustering structure from the fitted model,
# so we do not pass a cluster vector ourselves. See the note below.
robust_test <- coef_test(m, vcov = "CR2")
robust_test
```

::: {.callout-warning}
## Do not pass `cluster = star$gktchid` here

The obvious thing to write is `coef_test(m, vcov = "CR2", cluster = star$gktchid)`, and it fails with `arguments must have same length`.

The reason is the listwise deletion we looked at earlier in this chapter. `star$gktchid` has one entry per row of the *dataset*, while the model was fit on the smaller set of complete cases. The two vectors do not line up, and clubSandwich cannot tell which classroom each residual belongs to.

Omitting the argument is the reliable fix, because the fitted model already carries its grouping factor and knows which rows it used. If you do need to supply the cluster explicitly, take it from the model frame rather than the original data:

```r
mf <- model.frame(m)
coef_test(m, vcov = "CR2", cluster = mf$gktchid)
```

This is a specific instance of a general habit worth forming. Once a model has been fit, prefer `model.frame()`, `augment()`, or the model object itself over the data frame you started with. Anything derived from the original data risks being the wrong length.
:::

```{r}
# The model with the most influential clusters removed
flagged <- cook_df |> filter(cooks_d > cutoff) |> pull(gktchid)
```

```{r}
modelsummary(
  list("Original" = m, "Outliers removed" = m_trimmed),
  stars = c("*" = .05, "**" = .01, "***" = .001),
  gof_map = c("nobs", "aic", "bic"),
  title = "Robustness of the class type estimate to influential clusters"
```

Focus on the class type coefficient across the columns. If it stays essentially the same in magnitude, direction, and significance, you have an answer to the reviewer who worries about your residuals: the conclusion does not depend on the assumption in question. That is a far stronger response than asserting that the assumption was met.

## Writing it up

A sensitivity analysis paragraph belongs in nearly every quantitative paper, and it has a predictable shape. State which diagnostics you examined. Report what they showed, honestly, including the parts that looked imperfect. Describe the robustness checks you ran. Then state whether your substantive conclusion held.

The version that reads as defensive says the assumptions were met and moves on. The version that reads as competent concedes that residuals showed mild right skew and 14 classrooms exceeded the conventional Cook's distance threshold, then reports that the class size estimate changed by less than a tenth of a point under cluster-robust standard errors and with those classrooms excluded. The second version is more honest and considerably more persuasive.
